A controlled layer in between

An endpoint is only the beginning.

Keep provider requests separate from application availability. Decide what gets through, then make delivery observable.

  1. 01

    Receive & verify

    Give providers a stable endpoint. Check signatures against the original request bytes and shape your response with TypeScript.

  2. 02

    Store & process

    Accepted events and their processing jobs are committed together. Route through configured destinations with versioned code.

  3. 03

    Deliver & recover

    Inspect outgoing attempts and responses. Retry failed deliveries or replay an event against a chosen publication.

A few useful details

Know what you're
building on.

Does Payload Bay guarantee exactly-once delivery?

No. Delivery is at least once, so receivers must deduplicate. Retries, replay and recovery can result in repeat delivery.

Can I bring my own verification and routing logic?

Yes. Ingress and processing handlers are TypeScript, with shared helpers, middleware and immutable publications. Outgoing HTTP uses configured, tracked destinations.

Is the alpha ready for unrestricted public script execution?

No. The current deployment model trusts script publishers and uses a restricted Docker executor. Hardened hostile-tenant execution is a separate validation gate.

Where can I follow development?

Read the source and release notes on GitHub, report reproducible issues, or join the organization discussions. Contributions and concrete feedback are welcome.
